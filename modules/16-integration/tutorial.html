01 — The Big Analogy

The building inspector's final walkthrough

Module 1 was an elevator with 68 buttons, mostly locked, one door working. Fifteen modules later, every button is wired. This module is the inspector's final walkthrough: press every single button, confirm every floor actually opens (not just that the panel stopped announcing "floor not installed yet"). Then — because a building inspector's word alone isn't worth much — invite a second, independent inspector who's never seen these blueprints: a real, live web browser. Hand them the same building and see if they report the same floors in the same order.

02 — What Happens, Step by Step

  1. Force every one of the 68 states directly, one at a time, and confirm none of them still throws the "not implemented" error Module 1 built as a tripwire fifteen modules ago.
  2. Run a complete, realistic HTML document — doctype, comment, nested tags, attributes, entities in two different contexts, a self-closing tag — through the whole tokenizer in one continuous pass, starting from plain Data state, and check the exact resulting token sequence.
  3. Take that exact same document and hand it to a real browser's DOMParser, live. Compare tag sequence, attribute values, and decoded text, dimension by dimension.
  4. Deliberately construct a case this course has predicted a pure tokenizer cannot handle correctly — a <script> tag containing ordinary JavaScript with a < comparison — and check it against the same real browser too, to see the predicted divergence actually happen, not just describe it.

Getting a blank or broken result?

"my completeness check fails for a state I thought was finished" — check the dispatch chain in step() actually has an if branch for it, and that the branch calls the right method name (a typo'd method name is a silent no-op in some languages, a compile error in others — see this module's own DECISIONS.md for a real example of this exact class of mistake, caught by running the code).
"my Java test run stops partway with no summary line" — this is a real, documented behavior, not a bug in your code necessarily: an uncaught exception anywhere in TokenizerTest.main() terminates the whole run before Check.summary() executes, unlike JS's node:test, which isolates each test. See DECISIONS.md.

07 — Brain Exercise

Before reading the answer: this module found that JavaScript's test runner isolates failures (one broken test doesn't stop others from running) while this course's hand-rolled Java test harness does not (one uncaught exception kills the whole run). Given that difference, which harness's "all tests passed" claim should you trust more — and why might the answer be less obvious than it first seems?

Reveal the answer

It's genuinely not simply "JS's is better." JS's isolation means a green run tells you specifically "every test that ran, passed" — but it can never tell you a test was silently skipped due to a setup problem elsewhere, since each test is independent by construction. Java's lack of isolation is a real weakness for *diagnosing* failures (you lose information about everything after the crash) — but a Java run that reaches Check.summary() and prints "N passed, 0 failed" is actually a slightly *stronger* end-to-end guarantee in one specific way: it proves the entire file executed top to bottom without a single uncaught exception anywhere, not just that each isolated test block individually survived. Different tools, different guarantees — the right lesson isn't "pick a favorite," it's knowing exactly what a green run from each one is, and isn't, telling you.

08 — There Are No Dumb Questions

Q: If this tokenizer diverges from a real browser on <script> content, doesn't that mean it's "wrong"?
A: Not wrong — incomplete, in a specifically scoped, deliberately documented way. This course's Track 1 explicitly builds a standalone tokenizer, and the spec itself defines script-data-mode switching as tree construction's responsibility, not the tokenizer's. A pure tokenizer that DID special-case "script" internally would actually be less spec-faithful, not more — it would be quietly reimplementing tree-construction logic inside a layer that isn't supposed to have it.
Q: Why compare against a live browser at all, instead of just trusting fifteen modules of individually-passing tests?
A: Because individually-correct pieces composing into a correct whole is exactly the kind of claim that deserves independent verification, not just internal self-consistency — every module's tests were written by the same process that wrote the implementation, so they share any misunderstanding of the spec that process might have had. A real browser has no such shared blind spot; agreement with it is evidence from a genuinely independent source.
Q: Now that Track 1 is complete, what's actually missing to make this a "real" HTML parser?
A: Tree construction (turning the token stream into a DOM tree, including the state-switching feedback loop Module 9 identified), then everything downstream of that — CSS, layout, rendering. This course's Track 2 builds a deliberately minimal version of just the first piece, specifically to prove the tokenizer/tree-construction boundary this whole course has been pointing at since Module 9, not to build a production parser.
