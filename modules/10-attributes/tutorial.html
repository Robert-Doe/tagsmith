01 — The Big Analogy

A form with a "no duplicate fields" rule, enforced at submission time

Picture filling out a paper form where you can write as many label-and-answer pairs as you want in the margin — "color: blue," "size: large," and so on. But there's a clerk standing over your shoulder who, the instant you finish writing a label (before you've even started the answer), checks it against every label you've already written. Write "color" a second time, and the clerk stops you right there: "already have one of those — this one doesn't count," circles it as a note-to-self, and lets you keep writing the answer anyway, just so nothing jams. Only your very first "color" ever makes it onto the official form.

02 — What Happens, Step by Step

  1. After a tag name, whitespace or almost anything else means an attribute is starting. A scratch {name, value} pair begins building — not yet attached to the tag.
  2. Letters accumulate into the scratch name (lowercased as they go, exactly like tag names). The moment a terminator (whitespace, /, =, >, EOF) arrives, the name is finished — and only now does the duplicate check happen, comparing against every attribute already committed to the tag.
  3. No duplicate: the scratch pair is pushed onto the tag's real attribute list. Duplicate: a parse error is reported, and the pair is quietly dropped — never attached.
  4. An = after the name means a value is coming: skip whitespace, then look for a quote character (or, absent one, start reading an unquoted value immediately).
  5. Characters accumulate into the (already-committed-or-dropped) pair's value field, one at a time, until the closing quote (or, for unquoted, whitespace/>) ends it.
  6. >, from almost any of these states, emits the tag and returns to Data — unconditionally, no appropriateness check needed.

04 — The Algorithm, Explained (pseudocode)

function FINISH_ATTRIBUTE_NAME(tokenizer, nextState):
    isDuplicate = tokenizer.currentToken.attributes.any(a => a.name == tokenizer.currentAttribute.name)
    if isDuplicate:
        reportParseError("duplicate-attribute")
        // NOT pushed -- silently dropped, parsing continues
    else:
        tokenizer.currentToken.attributes.push(tokenizer.currentAttribute)
    tokenizer.state = nextState

function ATTRIBUTE_NAME_STATE(tokenizer):
    c = tokenizer.consume()
    if c in {TAB, LF, FF, SPACE}: FINISH_ATTRIBUTE_NAME(tokenizer, AFTER_ATTRIBUTE_NAME); return
    if c in {'/', '>'} or c == EOF:
        FINISH_ATTRIBUTE_NAME(tokenizer, AFTER_ATTRIBUTE_NAME)
        reconsume c there (no-op if EOF)
        return
    if c == '=': FINISH_ATTRIBUTE_NAME(tokenizer, BEFORE_ATTRIBUTE_VALUE); return
    // uppercase -> lowercase, NUL -> U+FFFD, else -> append as-is
    tokenizer.currentAttribute.name += normalize(c)

Getting a blank or broken result?

"my duplicate attribute keeps the SECOND value, not the first" — check finishAttributeName/its Java equivalent is comparing against attributes already pushed BEFORE pushing the new one, and skipping the push entirely on a match — not overwriting an existing entry.
"boolean attributes show value: undefined/null instead of empty string" — currentAttribute must be initialized with value: '' / "" up front, not left unset until a value state actually runs.

07 — Brain Exercise

Before reading the answer: the duplicate check compares the new attribute's name only against attributes already on the tag — not against every attribute name seen so far in the whole document, and not against attribute names on other tags. Why does the comparison need to be scoped to "this one tag" specifically, and what would go wrong if it weren't?

Reveal the answer

Because the rule is about a single element having two conflicting values for the same attribute at once — "duplicate" only means anything within the boundary of one tag's own attribute set. If the check compared against every attribute name ever seen in the whole document, then writing class on a second, completely unrelated <div> later in the page would incorrectly get flagged and dropped — which would make attributes essentially unusable past the first tag that used any given name. The fix in this module's code is almost invisible: currentToken.attributes only ever holds the attributes of the tag currently being built, and gets replaced with a fresh empty list every time a new StartTagToken/EndTagToken is constructed (Module 9). Getting the *scope* of a check right is often as important as getting the check's logic right.

08 — There Are No Dumb Questions

Q: Why is the duplicate check done at "finish the name" time, instead of just checking once right before the whole tag is emitted?
A: Doing it earlier means the discarded duplicate's VALUE never has to be specially discarded later — since the pair was never pushed onto the real attribute list in the first place, its value characters get written into an object that's already known to be headed for the void, with no extra bookkeeping needed to "remove" anything at emit time. Checking earlier turns a two-step process (detect-then-remove) into a one-step process (detect-then-never-add).
Q: In <div a="1" a="2">, does the tokenizer at least warn that "a" was skipped a second time via its value, "2"?
A: The parse error is reported once, at the moment the duplicate NAME is detected — the value "2" that follows is still tokenized character-by-character (into the orphaned, discarded attribute object) but produces no separate error of its own; the spec doesn't consider each subsequent character of a doomed attribute's value independently newsworthy once the name itself already triggered the one relevant parse error.
Q: This module handles three different quoting styles with three different states. Why not just one state that "looks for whatever character it started with"?
A: That's actually very close to what happens: `attributeValueQuotedState` (Module 10's own JS/Java code) IS one shared method parametrized by which quote character closes it, called by two one-line wrappers for double- and single-quoted. The unquoted state genuinely needs to be separate, though, since its termination condition (whitespace or `>`, not a matching quote) and its NUL/`&` handling interact differently with what "the end of the value" even means.
