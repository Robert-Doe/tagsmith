01 — The Big Analogy

A passport control officer with one very specific stamp

An immigration officer checks a passport: name, and optionally two supporting reference numbers (a "public" registry number, a "system" file number). Most travelers only show the name. Some show name plus one reference number. A few show both. The officer accepts all three combinations without blinking — that's completely normal. But the instant something looks tampered with — a name that's missing entirely, a reference number with no closing quote on its supporting document — the officer doesn't just note an error and move on. They stamp the passport "UNRELIABLE — VERIFY MANUALLY," a stamp that follows this traveler through every subsequent checkpoint. That stamp is forceQuirks.

02 — What Happens, Step by Step

  1. Module 12 already consumed DOCTYPE. A name is expected next — most real doctypes are just <!DOCTYPE html>, nothing more.
  2. After the name, check: does what follows spell PUBLIC or SYSTEM (any case)? If neither, and it isn't >, the whole rest of the declaration is malformed — force quirks, discard everything until >.
  3. PUBLIC expects a quoted public identifier, optionally followed by a quoted system identifier. SYSTEM alone expects just a system identifier.
  4. Every one of these sixteen states has its own EOF branch, but they're all identical: force quirks, emit whatever's been built so far, emit an EOF token, stop.
  5. One single state — the moment right after a COMPLETE, validly-quoted system identifier — treats leftover garbage before > as harmless noise instead of a reason to force quirks.

04 — The Algorithm, Explained (pseudocode)

function AFTER_DOCTYPE_NAME_STATE(tokenizer):
    c = tokenizer.consume()
    if c in {TAB, LF, FF, SPACE}: return          // ignore, stay
    if c == '>': emit tokenizer.currentToken; tokenizer.state = DATA; return
    if c == EOF: forceQuirksAndEmit(tokenizer); return

    tokenizer.pos -= 1                              // un-consume for lookahead
    if tokenizer.matchCaseInsensitive("PUBLIC"):
        consume 6 characters
        tokenizer.state = AFTER_DOCTYPE_PUBLIC_KEYWORD
        return
    if tokenizer.matchCaseInsensitive("SYSTEM"):
        consume 6 characters
        tokenizer.state = AFTER_DOCTYPE_SYSTEM_KEYWORD
        return

    reportParseError("invalid-character-sequence-after-doctype-name")
    tokenizer.currentToken.forceQuirks = true
    tokenizer.state = BOGUS_DOCTYPE

Getting a blank or broken result?

"my PUBLIC-only doctype has forceQuirks=true" — a missing system identifier when only PUBLIC was specified is NOT an error; double-check you're not accidentally forcing quirks just because systemIdentifier stayed null.
"case-insensitive PUBLIC/SYSTEM matching consumes the wrong characters" — check afterDoctypeNameState actually backs up pos by one BEFORE calling matchCaseInsensitive, since it already consumed one character to rule out the simple cases first.

07 — Brain Exercise

Before reading the answer: this module treats "no system identifier when only PUBLIC was given" as completely normal, but treats "no public identifier at all when PUBLIC was written" (i.e. PUBLIC immediately followed by something that isn't a quote) as a force-quirks error. Both cases involve a "missing" identifier — why does one get to just be null, and the other forces quirks?

Reveal the answer

Because the two situations tell you completely different things about authorial intent. Writing PUBLIC "..." with nothing after is a deliberate, common, historically valid choice — the author explicitly invoked the PUBLIC form and gave exactly what it requires (a public identifier), then stopped; there was never a promise of a system identifier to begin with. Writing PUBLIC followed by something that isn't a quote at all means the author invoked a keyword that specifically REQUIRES an identifier to immediately follow, and then didn't supply one — that's not "choosing not to include an optional piece," it's "starting a required piece and failing to finish it." The force-quirks flag consistently tracks the second kind of failure, not the first.

08 — There Are No Dumb Questions

Q: In practice, do modern web pages even use PUBLIC/SYSTEM doctypes anymore?
A: Almost never by choice — the modern, universally recommended doctype is the bare <!DOCTYPE html> this module's simplest test covers. The PUBLIC/SYSTEM machinery exists for backward compatibility with HTML 4.01 and XHTML-era documents, which is exactly why a tokenizer built today still needs to handle it correctly: old documents don't stop existing just because authoring conventions moved on.
Q: Why does Bogus DOCTYPE state have no data field, when Bogus Comment (Module 12) does?
A: Because a bogus comment's entire purpose is preserving arbitrary salvaged text as the comment's content — that's the whole point of a comment. A doctype's meaningful content is its name and identifiers, which by the time BOGUS_DOCTYPE is reached, are already either correctly captured or correctly marked missing; whatever garbage follows before > genuinely has nowhere useful to go, so the spec just discards it.
Q: Does this course's tokenizer decide whether a document renders in quirks mode?
A: No — this tokenizer only ever sets the forceQuirks FLAG on the token; deciding what quirks mode actually means for rendering (looser CSS box-model rules, different table layout algorithms, etc.) happens in tree construction and the rendering engine, both outside this course's Track 1 scope. This is the same tokenizer/tree-construction boundary Module 9 first drew for RCDATA switching, showing up again here for a completely different feature.
