01 — The Big Analogy

The doorman's counting trick, a fourth time — with a twist ending

This is the same doorman from Module 7, counting dashes to know when to open the door. But this doorman has one more quirk their script-data cousin didn't: if, right as the bell should ring, they instead hear an exclamation mark, they don't panic — they treat it as one more chance to close, just through a slightly unusual side door. Ring the bell after that exclamation mark, and the door still opens (with a note in the log: "that was an odd way to ask"). Say anything else instead, and the doorman shrugs, writes down everything they'd been provisionally holding onto — dashes, exclamation mark, all of it — as if it were never a knock at all, and goes back to just listening to ordinary conversation.

02 — What Happens, Step by Step

  1. Module 12 already consumed <!-- and created an empty comment token. Zero dashes are "pending."
  2. Count dashes: zero, one, two-or-more — the same three-state pattern Modules 7 and 8 already used for <script>'s hidden comments.
  3. From two-or-more dashes, > closes normally. A third (or fourth, or fifth) dash just keeps waiting. Anything else gives both confirmed dashes back to the data and starts counting from zero again.
  4. From two-or-more dashes, ! is a special detour: maybe this is the legacy --!> close.
  5. From that detour, > really does close the comment (with a parse error). A following dash starts a brand-new count. Anything else gives back all three held characters (--!) as literal data.
  6. EOF, from any comment state, still emits the comment token — partial content is preserved, never silently dropped.

04 — The Algorithm, Explained (pseudocode)

function COMMENT_END_STATE(tokenizer):
    c = tokenizer.consume()
    if c == '>':
        emit tokenizer.currentToken
        tokenizer.state = DATA
        return
    if c == '!':
        tokenizer.state = COMMENT_END_BANG
        return
    if c == '-':
        tokenizer.currentToken.data += '-'   // a third+ dash: keep waiting
        return
    // anything else: BOTH confirmed dashes were never a real close
    tokenizer.currentToken.data += '--'
    tokenizer.state = COMMENT

Getting a blank or broken result?

"my extra-dash test is missing characters" — this is the single easiest mistake in this module: forgetting to append the dash in COMMENT_END's own '-' branch. See this module's own DECISIONS.md for a live, verified example of exactly this bug and which test catches it.
"--!> doesn't close my comment" — double-check COMMENT_END_BANG's '>' branch actually emits and switches to Data (with a parse error) rather than treating it as a hard failure.

07 — Brain Exercise

Before reading the answer: Modules 7, 8, and 13 all build a dash-counting mechanism for recognizing -->'. But only Module 13's version has the extra --!> detour — the script-data escape states in Modules 7 and 8 have no equivalent. Why would HTML comments specifically need to tolerate this legacy quirk, when the script-data hidden-comment mechanism (which is also, mechanically, an HTML comment) doesn't?

Reveal the answer

Because real, historical HTML comments in the wild — written directly by people and by early tools, going back to the very earliest days of the web — sometimes used --!> as a stylistic close, a convention borrowed from SGML comment syntax (HTML's ancestor markup language, where --!> and similar constructs had defined meaning). That legacy exists specifically for ordinary, human-authored comments. The hidden-comment mechanism inside <script> tags (Modules 7–8), despite being built from literally the same punctuation, was never something a human directly hand-wrote as a "comment" in the SGML sense — it's a browser-compatibility mechanism, not an authoring convention, so there was never a body of real-world --!>-terminated script content the spec needed to stay compatible with. Same-looking syntax, different real-world history, different spec treatment — a good reminder that "why does the spec do X" often has a historical answer, not a logical one.

08 — There Are No Dumb Questions

Q: Does this module change what a well-formed comment (just <!--text-->, nothing weird) looks like at all?
A: No — every edge case this module handles (abrupt closes, extra dashes, the "--!" detour) only matters for MALFORMED or unusual comment syntax. A comment written the ordinary way tokenizes through the same states, but never touches any of the "give back what I provisionally swallowed" logic at all.
Q: Why does an unclosed comment at EOF still emit a token, when an unclosed TAG (Module 9) doesn't?
A: A tag's entire meaning depends on structural pieces that might still be incomplete at EOF — a name that's still being typed, attributes mid-value, nothing usable yet. A comment's meaning is just "whatever text is inside it," which is already fully formed and usable the instant you have ANY of it, complete or not. Emitting a truncated comment loses nothing that was ever going to be structurally meaningful; emitting a truncated tag would misrepresent something that was never finished.
Q: Is a bogus comment (Module 12) tokenized any differently once it reaches the tree-construction stage, compared to a "real" comment from this module?
A: Not by anything this course's Track 1 tokenizer does — both are plain CommentTokens with no distinguishing marker. Any downstream difference in how a real HTML processor treats them would have to come from something outside the token itself, like a diagnostic tool cross-referencing this tokenizer's separately-recorded parse-error log.
