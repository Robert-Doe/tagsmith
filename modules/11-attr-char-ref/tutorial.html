01 — The Big Analogy

The same interpreter, one extra caution — but only on the job site

Meet the same phrasebook interpreter from Module 4. Off duty, reading a novel (Data state), they translate confidently: see "amp" without its usual trailing punctuation, and they'll still confidently call it "and," same as always. But put that interpreter on a construction site (an attribute value), where "amp" might actually be the start of someone reading out a form code like "amp=47" — a real code, not a word — and they suddenly get cautious. On the job, if "amp" is immediately followed by an equals sign or another letter or digit, they refuse to guess: "that might not be the word I think it is — I'll just repeat exactly what I heard, untranslated." Off the job site, that same caution never kicks in.

02 — What Happens, Step by Step

  1. Module 10 already remembered which attribute-value state to return to, and which quote character (if any) shouldn't be swallowed by a reference attempt.
  2. Run Module 4's exact algorithm — named lookup, numeric decode, all of it, completely unchanged.
  3. New check, named-reference path only: if the match had no trailing semicolon, peek at the very next character. Is it = or alphanumeric?
  4. If yes: undo the entire match, as if it never started. The & and everything after it stay exactly as typed.
  5. If no (or if there was a semicolon, or it's a numeric reference): decode normally, exactly like Module 4.
  6. Append whichever result you got — decoded text, or a literal & — directly onto the attribute's value string. Nothing here ever becomes a separate character token.

04 — The Algorithm, Explained (pseudocode)

function CONSUME_NAMED_REFERENCE(tokenizer, isInAttribute):
    // ... find the longest matching name, exactly like Module 4 ...
    if match found:
        hasSemicolon = match.endsWith(';')
        if not hasSemicolon and isInAttribute:
            next = characterRightAfterTheMatch
            if next == '=' or isAlphanumeric(next):
                tokenizer.pos = positionRightAfterTheAmpersand   // undo everything
                return NO_MATCH
        // otherwise: proceed exactly as Module 4 always has
        commit the match, report missing-semicolon if needed
        return decoded value
    return NO_MATCH

07 — Brain Exercise

Before reading the answer: this exception exists "for historical reasons," per the spec's own words — protecting old-style query strings like href="page.cgi?a=1&=2" from being wrongly decoded. But modern, correctly-authored HTML almost always writes &amp; (with the semicolon) precisely to avoid this ambiguity in the first place. Given that, does this exception actually matter for HTML written today?

Reveal the answer

It matters enormously for HTML a browser receives, even if it matters little for HTML a careful author writes today — because a browser's tokenizer has to correctly handle every URL and query string that was ever generated, by any tool, at any point in the web's history, often without semicolons, often auto-generated by server-side code that predates modern authoring conventions. This is the same theme Module 7 surfaced with the script-data escape mechanism: the tokenizer's job isn't to reward well-formed input, it's to produce deterministic, spec-defined output for any input, including input shaped by decades-old conventions nobody would choose to write today. A comprehensive exam question along these lines is really testing whether you understand why the spec is as detailed as it is, not just whether you can recite the rule.

08 — There Are No Dumb Questions

Q: Why does the ambiguous check only look at ONE character after the match, instead of checking whether the rest of the value looks like a query string?
A: Because the tokenizer has no concept of "the rest of the value looks like a query string" — it only ever sees one character at a time, with no lookahead beyond what a specific state explicitly requests. The one-character check is the maximum context the algorithm is built to use anywhere, and it turns out to be sufficient: `=` or an alphanumeric character immediately following is specifically what makes a human (and this rule) suspect "this wasn't meant to be an entity."
Q: Could this exception ever cause a REAL entity reference to be wrongly left undecoded?
A: Only for the legacy no-semicolon spelling specifically — always writing the semicolon (`&amp;`, not `&amp`) sidesteps the ambiguity completely, which is exactly why modern authoring guidance universally recommends the semicolon form. The exception exists to protect a specific historical spelling convention, not to make correctly-written references unreliable.
Q: This module reused Module 4's function instead of writing a separate one for attributes. Was that the right call, given how different the two behaviors are?
A: The behaviors differ by exactly one `if` block inside one sub-function — everything else (numeric decoding, the bail-out terminators, longest-match search) is identical. Duplicating the whole algorithm to isolate one conditional would have meant two places to keep in sync for every future fix, for a much smaller actual difference than it might first appear.
