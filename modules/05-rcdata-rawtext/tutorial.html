01 — The Big Analogy

The security guard who only recognizes ONE badge

Imagine a room ("RCDATA," standing in for the inside of a <textarea>) with a security guard at the door. Once you're inside, the guard treats absolutely everything you say as ordinary conversation — including if you shout "there's a fire, everyone leave through the tag door!" That phrase alone doesn't open the door. The only thing that opens the door is showing the exact badge that matches the name written on the room's entrance sign — say the room is labeled "textarea," then only a badge that spells out exactly "" works. A badge that starts right (</text) but trails off wrong, or matches a completely different room's name (</title>), gets rejected — and everything you already said while showing that failed badge gets treated as if you'd just been talking the whole time, badge included.

02 — What Happens, Step by Step

  1. Inside RCDATA or RAWTEXT, ordinary characters become CharacterTokens exactly like Data state — with one difference: RAWTEXT never treats & as special.
  2. Seeing < doesn't commit to anything yet — it only switches to a "less-than-sign" state that peeks at the very next character.
  3. If that next character isn't /, the attempt is abandoned instantly: emit a literal <, go right back to RCDATA/RAWTEXT, and re-examine that same character fresh.
  4. If it is /, commit further: start building a candidate end tag name, one letter at a time, into both a real (possible) EndTagToken and a plain text buffer.
  5. The moment a terminator character (whitespace, /, >) is seen, check: does the name built so far exactly match the name of whatever tag opened this section?
  6. If yes: this really is the closing tag. Emit it, and switch all the way back to Data state (leaving RCDATA/RAWTEXT entirely). If no: none of this was real markup after all — dump everything gathered as literal text, and go back to RCDATA/RAWTEXT to reprocess the terminator character normally.

03 — A Concrete Map of This Module's State

The four-state chain shared by both families:

RCDATA / RAWTEXT
--'<'-->
less-than-sign
--'/'-->
end-tag-open
--letter-->
end-tag-name

Any step that doesn't match its arrow's condition immediately abandons the attempt and returns to RCDATA/RAWTEXT, dumping whatever was tentatively gathered as literal text.

04 — The Algorithm, Explained (pseudocode)

function END_TAG_NAME_STATE(tokenizer, returnState):
    c = tokenizer.consume()             // may be EOF
    isAppropriate = tokenizer.currentToken.tagName == tokenizer.lastStartTagName

    if isAppropriate and c in {TAB, LF, FF, SPACE}:
        tokenizer.state = BEFORE_ATTRIBUTE_NAME
        return
    if isAppropriate and c == '/':
        tokenizer.state = SELF_CLOSING_START_TAG
        return
    if isAppropriate and c == '>':
        emit tokenizer.currentToken
        tokenizer.state = DATA
        return

    if c is an ASCII letter:
        tokenizer.currentToken.tagName += lowercase(c)
        tokenizer.tempBuffer += c
        return                            // stay in this state, keep building

    // bail out: not actually a closing tag
    emit CharacterToken('<')
    emit CharacterToken('/')
    for bufChar in tokenizer.tempBuffer: emit CharacterToken(bufChar)
    tokenizer.state = returnState
    reconsume c in returnState            // no-op if c was EOF

Getting a blank or broken result?

"my end tag never matches, even with the right name" — check you set lastStartTagName (or called setLastStartTagName in Java) before calling run(), and that it's lowercase — the algorithm lowercases the tag name as it builds it, so an uppercase expectation will never match.
"characters are missing after a failed match" — check the reconsume step actually decrements pos by exactly one, and only when the failing character wasn't EOF.

07 — Brain Exercise

Before reading the answer: the "appropriate end tag token" check compares against lastStartTagName, a single value tracked globally on the tokenizer — not, say, a stack of open tag names. Given that HTML allows nesting, why is a single value enough here, when it clearly wouldn't be enough for matching arbitrary nested tags in general?

Reveal the answer

Because RCDATA and RAWTEXT sections can never nest, by construction — once you're inside a <textarea>, there is no such thing as a second, inner <textarea> "opening" (a literal <textarea> typed inside a textarea is just text, not a new tag, precisely because RCDATA doesn't parse tags at all until it sees a matching close). Since only one of these sections can ever be "open" at a time, there's only ever one name that could possibly be relevant — the name of whichever single tag most recently caused the tokenizer to enter this mode. A stack would be solving a problem that structurally cannot occur here. (Contrast this with the tree-construction stage, one layer up, which very much does need a stack — for regular nested elements. That's Track 2's Module A1.)

08 — There Are No Dumb Questions

Q: If </title> doesn't close a <textarea>, what DOES eventually close it, if the author forgets the closing tag entirely?
A: Nothing, within the tokenizer's rules — the section runs to the actual end of the document, and the whole rest of the file becomes RCDATA text. This is a real, well-known real-world footprint: a forgotten </textarea> can swallow the rest of a page. It's one of the clearest illustrations of why the tokenizer can't "look ahead" to fix author mistakes; it only ever reacts to what it has actually seen so far.
Q: Why does a failed match need to replay the buffered characters as INDIVIDUAL CharacterTokens instead of one bigger token?
A: Because Module 1 already decided a Character token holds exactly one character — this module didn't get to make a new decision here, it just had to stay consistent with that constraint while implementing a state that happens to accumulate multiple characters before deciding whether to keep them.
Q: Is PLAINTEXT actually used in real websites today?
A: Extremely rarely as deliberate authoring — but browsers still implement it, because HTML parsing rules are effectively permanent once the web depends on them; removing "quirky" legacy behavior risks breaking some genuinely ancient page somewhere. It's a good concrete example of why HTML's parsing spec is as long and detailed as it is: not because anyone wants this complexity, but because compatibility demands it.
Q: This module builds real logic that depends on lastStartTagName, which nothing sets yet. Isn't that backwards?
A: It's the same "prove the consumer before the producer exists" pattern this course has used since Module 1 (testing COMMENT_START before Module 13, testing CHARACTER_REFERENCE_IN_RCDATA before RCDATA existed in Module 4). Building consumers first and verifying them against manually-set test fixtures is what lets each module be independently, provably correct — rather than only testable once all 68 states are finished.
