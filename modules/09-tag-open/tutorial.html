01 — The Big Analogy

A mail sorter who never reads the letters

Picture a postal worker whose entire job is: look at the address on the outside of an envelope, decide which numbered bin it goes in, and drop it there — without ever opening the envelope or knowing what's inside, or what the recipient does with it. That worker is this module. When it sees <textarea> go by, it correctly bins it as "a start tag named textarea" — full stop. It has no idea, and no way of knowing, that somewhere down the line, a completely different department (tree construction — not part of this course's Track 1 at all) is going to read that label and say "oh, this means the mail carrier should switch to a special truck route for a while." The sorter's job ends the moment the envelope hits the bin.

02 — What Happens, Step by Step

  1. Data state already consumed < and switched here.
  2. An ASCII letter means a real tag is starting — create a fresh StartTagToken (or, from the / path, EndTagToken), and reconsume that same letter in Tag Name state.
  3. Tag Name state consumes letters one at a time, lowercasing uppercase ones, building up tagName.
  4. > unconditionally emits the tag and returns to Data state — no "is this the right tag" check happens here, unlike RCDATA/RAWTEXT/script-data's end-tag-name states.
  5. If the emitted token is a start tag, lastStartTagName gets updated — quietly fulfilling the contract Module 5 set up four modules ago.
  6. Then: back to Data state. Nothing about the tag name that was just parsed changes what state comes next. That decision belongs to a layer this course's Track 1 deliberately does not build.

03 — A Concrete Map of This Module's State

Where the state-switching decision actually lives:

Tree construction (Track 2, Module A1) — reads tokens, decides "this start tag named 'textarea' means: tell the tokenizer to switch to RCDATA now"
▲ tokens flow up, instructions flow back down ▼
This tokenizer (Track 1, Module 9) — emits a StartTagToken(tagName="textarea"), returns to DATA, and moves on. No memory of what "textarea" means.

04 — The Algorithm, Explained (pseudocode)

function TAG_NAME_STATE(tokenizer):
    c = tokenizer.consume()          // may be EOF
    if c in {TAB, LF, FF, SPACE}: tokenizer.state = BEFORE_ATTRIBUTE_NAME; return
    if c == '/':                     tokenizer.state = SELF_CLOSING_START_TAG; return
    if c == '>':
        emit tokenizer.currentToken   // UNCONDITIONAL -- no appropriateness check
        if currentToken is a StartTagToken:
            tokenizer.lastStartTagName = currentToken.tagName
        tokenizer.state = DATA
        return
    if c is uppercase ASCII letter:  currentToken.tagName += lowercase(c); return
    if c is NUL:                     currentToken.tagName += U+FFFD; return   // IN the name
    if c is EOF:                     emit EOFToken; halt              // token discarded
    currentToken.tagName += c

08 — There Are No Dumb Questions



  

    
Q: This seems like a strange way to design a tokenizer. Wouldn't it be simpler to just have it know about textarea/script/style directly?

    
A: It would be simpler for this one case, but it would break the tokenizer/tree-construction separation the rest of the spec depends on — tree construction sometimes needs to change the tokenizer's state for reasons that have NOTHING to do with the tag name alone (foreign content rules for SVG/MathML, for instance, which Module 15's CDATA section touches on). Keeping the tokenizer "dumb" about semantics and purely mechanical about syntax is what makes the two stages independently specifiable, testable, and — relevant to this course specifically — independently buildable as two separate tracks.

  

  

    
Q: Real browsers clearly DO render <textarea> content as raw text. If the tokenizer alone can't do that, how does it actually happen?

    
A: Exactly the mechanism this module's Brain Exercise points at: a real browser's tree constructor, upon receiving the StartTagToken for "textarea," issues an explicit instruction back to the tokenizer ("switch to RCDATA now") before any more input is consumed. It's a real, two-way feedback loop between the two stages, not two independent passes. Track 2's Module A1 builds a minimal version of exactly this loop.

  

  

    
Q: Why does U+FFFD replace NUL inside a tag name, but Data state just leaves NUL alone?

    
A: A character token's data IS visible text content in the final document — preserving the literal NUL there is at least consistent with "don't invent characters that weren't in the source." A tag name, by contrast, is never displayed as text; it's an internal identifier the tree constructor will compare against known element names. Embedding a literal NUL byte inside that identifier risks it being used in more sensitive processing than "displayed on screen," which is exactly the class of thing U+FFFD-substitution defends against — foreshadowing Track 2's Module A3 on parser-differential security issues.
