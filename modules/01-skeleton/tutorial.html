01 — The Big Analogy

Meet the elevator

You've just been handed the keys to a brand-new 68-floor building. Your job today is not to decorate a single floor. Your job is to wire the elevator panel — a physical button for every one of the 68 floors — so that pressing any button does something predictable, even though you haven't built a single floor yet.

You wire it like this: the ground floor button (let's call it "no one's here yet" — EOF) actually opens the doors, for real, right now. Every other button, when pressed, doesn't jam and doesn't stay silent. It lights up and announces, loudly and specifically: "Floor 47 — Comment start — isn't built yet. Construction crew arrives in Module 13."

That's the whole job. An honest, fully-labeled, mostly-locked building, with exactly one door that already opens for real.

02 — What Happens, Step by Step

  1. A Tokenizer is constructed with an input string. It sets a position pointer to 0 and its current state to DATA — the spec's mandated starting state.
  2. The main loop calls step() repeatedly until a flag says halted.
  3. step() checks the current state. Only one branch has real logic: DATA. Every other state falls through to a lookup: "which module owns this floor?" — and throws, naming it.
  4. Inside the DATA branch: first check, is there a next character at all? If not (EOF), emit an EOFToken and halt. The loop stops. This is the one door that really opens.
  5. If there is a next character, look at it. An & throws, naming Module 4. A < throws, naming Module 9. Anything else throws, naming Module 3 — the module that finishes the rest of this very state.
  6. Six token classes exist and can each be built and inspected directly, independent of the loop — proven by tests that never call run() at all for this part.

04 — The Algorithm, Explained (pseudocode)

This is language-agnostic — see js/CODE_WALKTHROUGH.md or java/CODE_WALKTHROUGH.md for exactly how each line below becomes real JavaScript or Java.

function RUN(input):
    tokenizer = new Tokenizer(input)
    while not tokenizer.halted:
        STEP(tokenizer)
    return tokenizer.tokens

function STEP(tokenizer):
    if tokenizer.state == DATA:
        DATA_STATE(tokenizer)
    else:
        moduleNumber = lookup(tokenizer.state)
        fail "not implemented", tokenizer.state, moduleNumber

function DATA_STATE(tokenizer):
    if tokenizer.atEOF():
        emit EOFToken
        tokenizer.halted = true
        return
    c = tokenizer.consume()
    if c == '&':
        fail "not implemented", "Character reference in data", 4
    if c == '<':
        fail "not implemented", "Tag open", 9
    fail "not implemented", "Data (character-emission branch)", 3

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Tokenize any real HTML text (even plain "hello" throws)
  • Decode a single character reference like &amp;
  • Recognize a single tag, attribute, comment, or doctype
  • Run this tokenizer against an actual web page

Can do

  • Prove the dispatch loop terminates correctly on empty input
  • Prove all 68 states are addressable and correctly labeled
  • Construct and inspect all 6 spec-defined token types
  • Fail loudly, specifically, and testably for anything unbuilt

07 — Brain Exercise

Before reading the answer: This module implements exactly one real branch — the DATA state's EOF check — out of everything in the entire 68-state machine. Why that branch, specifically? Module 9 ("Tag Name state") sounds, on paper, just as simple: read letters until you hit a space or >. Why not implement that early instead, since it looks like comparable effort?

Reveal the answer

Because Tag Name state doesn't start from nothing — the spec's own algorithm assumes you already arrived there from Tag Open state, with a half-built StartTagToken already sitting in a "current token" slot, and it assumes the initiating < character has already been consumed. Implementing Tag Name state first would mean fabricating that upstream state by hand just to test it — which quietly defeats the entire point of this course: verifying real integration between states, not a collection of logic snippets tested in isolation. The DATA state's EOF branch is the only piece of logic in the entire spec that requires zero upstream setup — it's reachable the instant the tokenizer is constructed. That's not a coincidence; it's why the spec itself designates DATA as the mandatory starting state.

08 — There Are No Dumb Questions

Q: Why throw an exception for unimplemented states instead of just returning a placeholder token?
A: A placeholder token would be silently wrong — code calling this tokenizer would keep running with garbage output and you might not notice for weeks. A thrown, named, numbered exception fails the instant something unbuilt is reached, which is exactly what you want while the "building" is still 67/68ths unbuilt.
Q: Do I really need 68 distinct state names? Couldn't the tokenizer just use numbers 1–68?
A: It could, mechanically — nothing about a finite state machine requires human-readable labels. But every error message, every test failure, and every debugging session in the next 15 modules will be dramatically faster to reason about if a crash says "Comment end bang" instead of "state 51." The cost (typing out 68 strings once, here) is paid entirely in this module.
Q: Real browsers don't throw NotImplementedError for anything — doesn't that mean this design is "wrong"?
A: Real browsers ship a spec-complete tokenizer, so there's nothing left unimplemented to throw about. This exception type is scaffolding specific to the process of building one incrementally, the way construction scaffolding exists on a building site but isn't part of the finished building.
Q: Why build all six Token classes now if five of them aren't used until later modules?
A: Because the spec defines all six in one preamble, before describing a single state — the token *shapes* aren't state-specific knowledge, they're shared vocabulary every state will eventually use. Building them once, now, and testing them directly (without needing a working tokenizer to produce one) is strictly less work than re-deriving each one's fields when its first consuming state shows up.
Q: What happens if I add a 69th state to my own State enum that isn't in the real spec?
A: Nothing stops you mechanically — but it would immediately fail the "State enum has exactly 68 states" test in both languages, which exists specifically to catch that. That test is a tripwire, not a formality.
