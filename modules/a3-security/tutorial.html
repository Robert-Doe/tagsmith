This module reuses Module A1's tag-name-to-state table for a second, distinct real spec purpose: not switching state mid-stream, but choosing the tokenizer's starting state before parsing even begins.

01 — The Big Analogy

The interpreter who forgot which room they're in

Imagine an interpreter fluent in two completely different conventions: in the courtroom, every word gets logged as sworn testimony; in the green room backstage, every word is just casual chat, off the record. The interpreter doesn't decide which convention applies by reading the words themselves — they're told, before anyone speaks, which room they're standing in. Now imagine someone scribbles down a sentence spoken backstage (off the record, harmless) and later hands that same transcript to a court stenographer, who — knowing nothing about where it came from — logs it as sworn testimony instead. Nothing was forged. The words never changed. Only the room did. This module is about exactly that failure mode, applied to HTML: the same text, genuinely inert in one parsing context, becomes live and dangerous the instant it's handed to a parser standing in a different room.

02 — What Happens, Step by Step

  1. A context tag name (e.g. textarea, div, script) is chosen before a single character of the fragment is parsed — mirroring exactly what element.innerHTML = string does in a real browser, which always knows its own target element in advance.
  2. The tokenizer's starting state (and lastStartTagName) is set directly from that context, using the very same tag-name table Module A1 built for a different purpose (mid-stream switching).
  3. The fragment is parsed completely normally from that starting point — nothing about the tokenizer's per-character logic changes at all.
  4. The same exact string is parsed twice, with two different context tag names, and the two resulting trees are compared directly.

03 — A Concrete Map of This Module's State

A real, live <img> element, with a real onerror handler. Same string. Different room.

04 — The Algorithm, Explained (pseudocode)

function PARSE_FRAGMENT(html, contextTagName):
    tokenizer = new Tokenizer(html)
    if contextTagName is not none:
        tokenizer.state            = CONTEXT_INITIAL_STATE(contextTagName)
        tokenizer.lastStartTagName = contextTagName
    // from here on: identical to a normal top-level parse
    return TREE_BUILD(tokenizer)

function CONTEXT_INITIAL_STATE(tagName):
    // the SAME table Module A1 uses for mid-stream switching --
    // applied here BEFORE parsing starts, instead of in reaction
    // to a start tag token appearing mid-stream
    if tagName in RCDATA_ELEMENTS:  return RCDATA
    if tagName in RAWTEXT_ELEMENTS: return RAWTEXT
    if tagName == "script":         return SCRIPT_DATA
    if tagName == "plaintext":      return PLAINTEXT
    return DATA

// The mutation-XSS mechanism itself:
safelyStored = PARSE_FRAGMENT(payload, "textarea")   // RCDATA -> inert text
capturedText = safelyStored.children[0].text          // identical to payload
reinserted   = PARSE_FRAGMENT(capturedText, "div")    // DATA -> LIVE element
// reinserted now contains a real, dangerous element -- built from text
// that was, one step earlier, provably inert

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Fix this mechanism — it isn't a bug to patch. Context-sensitive tokenizing is a real, intentional spec feature; the risk lives in application code that moves text between contexts without re-sanitizing for the destination, not in the tokenizer
  • Model the full real fragment-parsing algorithm (synthetic html/head/body wrapper elements, foreign-content namespace switching) — this module's simplified version is enough to prove the mechanism, not spec-complete
  • Cover other named real-world mXSS variants that depend on machinery this course deliberately left out of scope (foreign content, the "scripting flag" affecting <noscript>)

Can do

  • Prove, with a real parsed attribute list, that identical text is inert in one context and a live element with a live event handler in another
  • Prove the underlying mechanism against a real, live browser DOM — not just this course's own implementation
  • Explain, precisely, why "the text was safe when I first checked it" is not the same claim as "the text is safe wherever I put it next"

Getting a blank or broken result?

"my context='div' test still produces literal text, not a real element" — double check you're passing the context tag name as the SECOND constructor argument, not accidentally parsing it as part of the HTML string itself; and confirm `contextInitialState('div')` actually falls through all four checks to the `DATA` default (it isn't in any of the three special sets, and isn't `"script"`/`"plaintext"`).
"my captured text doesn't match the original payload exactly" — this specific payload contains no `&`/`<`-requiring-decode sequences, so RCDATA's entity-decoding (Module 4) never has anything to do here; if you change the payload to include a real entity like `&`, expect `capturedText` to differ from the raw source text — decoded, not verbatim — which is itself worth predicting before you test it.

07 — Brain Exercise

Before reading the answer: Module A2 built a real, correct, tokenizer-based sanitizer. Suppose an application runs `div.innerHTML = Sanitizer.sanitize(userInput)` (safe, by Module A2's own proof), reads the sanitized text back out with `div.textContent`, and later does `anotherDiv.innerHTML = thatCapturedText` somewhere else in the same page, with no further processing. Does Module A2's sanitizer guarantee `anotherDiv` is safe too?

Reveal the answer

No — and this is precisely the composition failure this module exists to name. Module A2's `sanitize()` guarantees its OWN output is safe HTML when parsed in an ordinary DATA-state document context, which is exactly what `div.innerHTML = sanitize(...)` gives you. But `div.textContent` reads back the ELEMENT TREE's decoded text — not the sanitized markup string — and reassigning that decoded text into a second element's `innerHTML` is a brand-new parse, in a context Module A2 never analyzed and never promised anything about. If `sanitize()`'s output happened to contain literal `<`/`>`-looking sequences that survived as safe TEXT the first time (say, inside a ``, exactly like Module A2's own proof case), reading that text back out and reinserting it verbatim can resurrect exactly the mechanism this module demonstrates.
