01 — The Big Analogy

The stenographer and the editor

Picture a courtroom stenographer (the tokenizer): she reads the proceedings one word at a time and shouts out each recognized unit the instant she's sure of it — "objection!", "sustained!", "witness name: Ms. Chen" — with zero awareness of the trial's overall structure. Now picture an editor (the tree constructor) sitting beside her, building the official transcript's outline from what she shouts. Most of the time the editor just listens and files things away. But every so often, the judge says something like "the witness will now read the contract aloud, verbatim" — and at that exact moment, the editor leans over and whispers to the stenographer: "for the next section, don't interpret anything as a courtroom command — even if it sounds like 'objection,' write it down as literal words, until you hear me say 'stop.'" That whisper is the entire missing piece from every earlier module in this course: this tokenizer could always shout tokens, but it never had an editor sitting next to it who could whisper instructions back. Module A1 builds that editor.

02 — What Happens, Step by Step

  1. A TreeBuilder owns a Tokenizer and asks it for exactly one step at a time — never the whole token stream at once — specifically so it can react before the tokenizer moves on.
  2. Every newly emitted token gets routed by type: a DOCTYPE token sets the document's doctype fields; a comment token becomes a CommentNode; a character token gets appended onto (or starts) a TextNode; a start tag becomes an ElementNode, attached to whatever element is currently "open"; an end tag closes the matching open element.
  3. The moment a start tag becomes an ElementNode, its tag name is checked against a small table. If it's one of a handful of special names (textarea, title, style, script, ...), the tree builder reaches directly into the tokenizer object and changes its state field, right then — before the tokenizer has consumed a single character of that element's content.
  4. Because the state change happens before the next character is read, the tokenizer now correctly treats everything up to the matching end tag as literal text (or script text), instead of trying to recognize tags inside it.

03 — A Concrete Map of This Module's State

The entire feedback table this module adds — small on purpose, see §05:

04 — The Algorithm, Explained (pseudocode)

function BUILD_TREE(html):
    tokenizer = new Tokenizer(html)
    document  = new DocumentNode()
    stack     = [document]        // "currently open" elements, root at index 0

    while not tokenizer.halted:
        countBefore = length(tokenizer.tokensSoFar)
        tokenizer.step()                      // produce AT MOST the next token
        for each newToken since countBefore:
            PROCESS(newToken, stack, document)

    return document

function PROCESS(token, stack, document):
    top = stack[last]
    match token.type:
        DOCTYPE:    document.doctype = fields_of(token)
        COMMENT:    append CommentNode(token.data) to top.children
        CHARACTER:  if top.children[last] is a TextNode:
                        top.children[last].data += token.data
                    else:
                        append new TextNode(token.data) to top.children
        START_TAG:
            element = new ElementNode(token.tagName, token.attributes)
            append element to top.children
            if token.selfClosing or token.tagName in VOID_ELEMENTS:
                return                          // never opened -- no children ever
            push element onto stack
            if token.tagName in TAG_TO_STATE_TABLE:            // <-- THE seam
                tokenizer.state             = TAG_TO_STATE_TABLE[token.tagName]
                tokenizer.lastStartTagName  = token.tagName
        END_TAG:
            walk stack top-down looking for an ElementNode with
              matching tagName; if found, pop the stack down to
              (and including) it; if not found, do nothing

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Handle genuinely misnested tags correctly (<b><i>x</b></i>) — the real spec's "adoption agency algorithm" reparents nodes; this module's stack-walk just closes down to the first match, silently dropping the rest
  • The real HTML5 "insertion modes" (before html, in head, in body, in table, ...) — this module has exactly one generic stack, no mode-specific rules
  • The complete RCDATA/RAWTEXT/void-element vocabulary — this module's table is a representative subset, not the full spec list (see DECISIONS.md)
  • Foreign content (SVG/MathML) context switching — a related but separate seam, out of scope here

Can do

  • Drive the real tokenizer one step at a time and intervene between steps — the exact producer/consumer coupling the spec itself describes
  • Correctly resolve both documented divergences from Module 16's real-browser differential test
  • Build a correct, real nested tree for ordinary, well-formed documents — doctype, elements, attributes, text, comments, void elements, self-closing tags

Getting a blank or broken result?

"my textarea/script content still gets split into multiple elements" — check that the state-switch happens inside insertStartTag, immediately after the element is pushed onto the stack, and specifically before control returns to the step-loop. If it's applied one iteration too late (e.g. after the loop that processes a batch of tokens, rather than the instant the start tag is seen), the tokenizer will already have consumed at least one more character in the wrong state.
"my Java build won't compile, complaining about halted" — that field is intentionally private; this module calls the new public isHalted() accessor instead of touching the field directly. See CODE_WALKTHROUGH.md.

07 — Brain Exercise

Before reading the answer: suppose, instead of stepping the tokenizer one call at a time, you called tokenizer.run() once to get the complete token list, and only then walked that finished list, applying the exact same PROCESS logic (including the state-switch line) to each token in order. For the input <textarea>x&amp;<b>y</textarea>, would the resulting tree still come out correct?

Reveal the answer

No — and the reason is subtle enough to be worth sitting with. The bug isn't in PROCESS's logic at all; it's that run() already finished tokenizing the entire input before your code gets to look at a single token. By the time run() returns, the tokenizer was still in plain DATA state when it reached <b> — nobody had told it otherwise yet — so it already produced a real StartTagToken("b") instead of the literal characters <, b, >. That token is now a fact in the list; no amount of clever post-processing of an already- finished, already-wrong token list can turn a StartTagToken back into the three characters it should have been. This is exactly why this module's run() method calls tokenizer.step() in a loop instead of calling the tokenizer's own, more convenient run() — the timing of the intervention, not just its existence, is what makes it work.

08 — There Are No Dumb Questions

Q: Did this module's tests actually pass on the first try, or is that just how it's being presented?
A: Not quite — and the real story is worth knowing. While preparing inputs for Module A2, <title><script>alert(1)</script></title> produced a genuinely broken tree: the tokenizer was closing <title> early, at the mismatched </script>, instead of treating it as literal text the way Module 5's "appropriate end tag" rule requires. Direct instrumentation traced it to a real bug that had existed in this course's shared Tokenizer.js since somewhere in Modules 5–9: two methods with the same name, endTagOpenState, where JavaScript's last-definition-wins class semantics silently let one shadow the other. No Track 1 test could ever have caught it, because Track 1 never drives a real, tag-triggered RCDATA/RAWTEXT/script-data entry followed by a genuinely mismatched closing tag — only this module's real tag-driven seam can. Full story, root cause, and the fix (plus why Java never had this bug at all) are in this module's DECISIONS.md.
Q: If the tokenizer already emitted the wrong token by the time the tree builder sees it, how can switching state "later" ever fix anything?
A: It doesn't fix a token that's already wrong — it prevents the next token from ever being wrong in the first place, by switching state before the tokenizer consumes the very next character. Token production is strictly one-directional (tokenizer → tree builder), but the tree builder is allowed to influence the tokenizer's future behavior — just never its past output. Sequence is everything here, which is exactly what the Brain Exercise above demonstrates concretely.
Q: This module already resolves both real divergences Module 16 found against a live browser — why still call it "minimal"?
A: Because the real fix needed here turned out to be small, but the real spec around it is not. HTML5's actual tree construction algorithm has roughly twenty named "insertion modes," each with dozens of tag-specific rules, plus a separate "adoption agency algorithm" just for misnested formatting elements. This module implements one generic open-elements stack and one small feedback table — enough to prove and resolve the exact seam this course has been pointing at since Module 9, not a production-grade tree builder.
Q: Is reaching directly into another object's field (`tokenizer.state = ...`) from outside its class bad design?
A: In most contexts, yes — it's usually a sign two things should talk through a method, not a shared field. Here it's deliberate and spec-faithful: the HTML5 spec itself describes tokenization and tree construction as two coupled algorithms that run concurrently and reach into each other, not two independent black boxes connected by a clean one-way interface. Modeling that coupling as a direct, visible field write is more honest about what's actually happening than hiding it behind a method that would just do the same assignment one layer removed.
