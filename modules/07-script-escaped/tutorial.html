01 — The Big Analogy

A doorman counting knocks

Once you're inside the hidden comment, a doorman starts listening for a very specific knock pattern to know when to let you back out: two knocks in a row, followed by the doorbell. He keeps a mental tally: "zero knocks so far... one knock... two knocks, I'm watching the bell now." But if anything else happens in between — someone coughs, talks, does literally anything that isn't another knock — he resets his tally back to zero and starts listening from scratch. Ring the bell without two fresh knocks first, and he doesn't even look up; the bell only means "open the door" if it's the very next sound after two consecutive knocks.

02 — What Happens, Step by Step

  1. Module 6 already emitted < and !. Seeing a - next commits toward the comment opener; anything else abandons it and rejoins plain script data.
  2. A second consecutive - completes <!-- and enters escaped mode already primed at "dash count: two."
  3. While escaped, ordinary text is literal (no character references, same as RAWTEXT/script data). Each - advances the dash count; anything else resets it to zero.
  4. > only means "close the comment" when the dash count is already two-or-more. Everywhere else, it's just a character.
  5. < while escaped might start a real </script> (checked via the same "appropriate end tag" mechanism as Modules 5–6) or might start a nested, literal <script — which hands off entirely to a different mechanism (Module 8), not a repeat of this one.
  6. EOF while still escaped is its own specific parse error — a never-closed hidden comment.

03 — A Concrete Map of This Module's State

The dash-counting sub-machine:

ESCAPED
(count: 0)
--'-'-->
ESCAPED_DASH
(count: 1)
--'-'-->
ESCAPED_DASH_DASH
(count: 2+)

Any character that isn't -, <, or NUL sends you straight back to "count: 0," from any of the three boxes. Only from the rightmost box does > mean anything special.

04 — The Algorithm, Explained (pseudocode)

function SCRIPT_DATA_ESCAPED_DASH_DASH_STATE(tokenizer):
    c = tokenizer.consume()      // EOF here -> parse error, emit EOF, halt
    if c == '-':
        emit CharacterToken('-')
        return                              // stay -- count remains "2+"
    if c == '<':
        tokenizer.state = SCRIPT_DATA_ESCAPED_LESS_THAN_SIGN
        return
    if c == '>':
        emit CharacterToken('>')
        tokenizer.state = SCRIPT_DATA        // the ONLY real exit
        return
    // anything else, including NUL: count resets to zero
    if c is NUL: reportParseError("unexpected-null-character")
    emit CharacterToken(c)
    tokenizer.state = SCRIPT_DATA_ESCAPED    // back to count: 0

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Handle a nested, literal <script>...</script> inside the hidden comment (Module 8)
  • Enter this whole mechanism from real markup — needs Module 9's <script> opening tag

Can do

  • Correctly tokenize a complete, real hidden-comment-wrapped script body
  • Correctly distinguish "close the comment" from "just a character that happens to be >"
  • Correctly close the whole script element via a matching end tag, even mid-comment

Getting a blank or broken result?

"--> doesn't close the comment" — check the dash count is actually reaching two before the > arrives; a single stray non-dash character anywhere in the run resets it, by design.
"my tests all pass but I suspect a bug" — see this module's own DECISIONS.md "What We Proved" section: a real bug was deliberately introduced during this module's own construction and slipped past the full test suite undetected. Green tests are not a correctness guarantee, only a coverage record.

07 — Brain Exercise

Before reading the answer: the spec could have defined "exit the hidden comment" as reacting to the exact three-character sequence -->` as a single unit, checked all at once. Instead, it's built as three separate states each reacting to one character at a time. What does the three-state version buy that a single "look for the whole sequence" check wouldn't?

Reveal the answer

Correct handling of a dash count greater than two, and correct behavior for a dash-run that's interrupted partway through — both of which are exactly the kind of case a naive "does the next three characters spell close it out?" check would get wrong or would need extra special-casing to handle. Input like ----> (four dashes) needs to still close correctly, and input like --x--> needs the count to correctly restart after the interrupting x. A three-state counter handles both automatically as a natural consequence of its structure, without needing to special-case either one — which is really the whole reason a state machine is the right tool for this problem in the first place, going all the way back to the Prerequisites page on finite state machines.

08 — There Are No Dumb Questions

Q: This seems like a lot of machinery for something that barely matters in modern web development. Is it worth knowing this deeply?
A: For day-to-day web development, no. For a comprehensive exam on browser tokenization specifically, this module is prime territory — it's the single clearest example in the entire spec of legacy compatibility requirements directly shaping present-day parsing rules, and it's exactly the kind of "why does the spec do THIS" question an examiner can ask that a surface-level reading wouldn't prepare you for.
Q: Why does a nested "<script" inside the hidden comment need a totally separate mechanism (Module 8) instead of just recursing into this same one?
A: Because the two situations aren't actually symmetric. This module's job is "recognize when the OUTER hidden comment closes." A nested <script>...</script> inside that comment needs its OWN closing recognized first, without prematurely triggering the outer comment's close — and critically, the outer close condition itself changes once you're inside a nested script (the spec requires seeing the nested </script> before "-->" is allowed to mean anything again). That's a genuinely different rule, not the same rule applied twice.
Q: Is "eof-in-script-html-comment-like-text" a real name from the spec, or did this course make it up?
A: It matches the real parse-error naming convention used in the modern WHATWG Living Standard for this exact situation. Naming it consistently with real spec terminology (rather than an invented description) is deliberate — it's meant to be a name you could search for in the actual spec and land on the relevant section.
