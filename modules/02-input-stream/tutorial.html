01 — The Big Analogy

Three keyboards, one typewriter

Imagine three different old typewriters were used to type up the same manuscript: a Mac one that hits "new line" with a single character, a Windows one that hits it with two characters back-to-back, and an old classic Mac OS one that uses yet another single character. If you handed a proofreader all three pages and said "read for line breaks," they'd have to carry three different rulebooks in their head at once — misery.

So before the proofreader (the tokenizer) ever starts reading, an editor retypes all three pages onto identical paper, using exactly one kind of line break throughout. Now the proofreader only ever needs to know one rule, forever, no matter which typewriter the original came from.

02 — What Happens, Step by Step

  1. Raw input text arrives, possibly containing CRLF (Windows-style), lone CR (old Mac-style), or already-correct lone LF (Unix-style) line endings — or any mixture of the three.
  2. Every CRLF pair (a CR immediately followed by an LF) is collapsed into a single LF.
  3. Any CR character still remaining after step 2 (i.e., one that was not part of a CRLF pair) is also converted to a single LF.
  4. The result — a string that provably contains zero CR characters — becomes the actual input the Tokenizer's pos/consume()/eof() machinery operates on.
  5. Every state built from here on (Module 3 onward) is now free to never special-case CR — it cannot occur.

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Tokenize any real tag, attribute, or entity — still Module 1's limits
  • Handle NUL characters or other spec-defined parse-error code points (Module 3)
  • Iterate by true Unicode code point instead of UTF-16 code unit (deferred, documented risk)

Can do

  • Accept Windows, old-Mac, or Unix line endings and normalize all three identically
  • Guarantee, provably, that no state downstream will ever see a CR
  • Keep every one of Module 1's original guarantees intact (all 8/14 original checks still pass)

07 — Brain Exercise

Before reading the answer: the two normalization passes run in a specific order — CRLF pairs first, lone CRs second. Suppose you swapped that order. Exactly how many of this module's test assertions would you expect to fail, and why not more (or fewer)?

Reveal the answer

Two, in both languages — not one, and not four. Only tests whose input contains an actual CRLF pair break, because swapping the order means the lone-CR pass runs first and turns the CR half of every CRLF pair into its own LF before the CRLF-pair pass ever gets a chance to see a CRLF sequence — by the time that second pass runs, there simply isn't one left to match, so nothing happens, leaving behind two LFs where one was required. Tests built only from lone CRs (no adjacent LF) are completely unaffected, because the lone-CR pass handles them correctly regardless of which pass runs first. This was verified by actually swapping the code, not reasoned about in the abstract — see DECISIONS.md's "What We Proved" section for the exact before/after counts.

08 — There Are No Dumb Questions

Q: Why does this matter today? Don't all text editors just use LF now?
A: Plenty of real-world HTML still arrives with CRLF — any file authored or edited on Windows, many HTTP responses, form submissions from browsers (which are required by other specs to send CRLF for line breaks in form data), and files round-tripped through certain version control configurations. A tokenizer that silently assumed LF-only would misbehave on a large fraction of real traffic.
Q: Couldn't Module 3's Data state just special-case CR itself, instead of a separate preprocessing step?
A: It could, mechanically — but then Module 3 wouldn't be the only place that needs to know about CR. Every future text-consuming state (RCDATA, RAWTEXT, script data, comments, attribute values, DOCTYPE identifiers — a dozen-plus states across a dozen-plus future modules) would each need the same special case, and each would be a chance to get it slightly wrong. Handling it exactly once, globally, before any state runs, is what lets every later module's DECISIONS.md correctly say "forced by spec, not re-derived."
Q: Is this preprocessing step itself part of the 68-state machine?
A: No — it's explicitly a separate step the spec describes before the state-machine section even begins. That's also why it isn't in the `State` enum and doesn't get a `NotImplementedError` module mapping; it's plumbing the state machine depends on, not one of its rooms.
Q: What about other whitespace or control characters — are those normalized too?
A: No, and that's deliberate — only line-ending characters get rewritten here. Other control characters (like NUL) are left completely intact by preprocessing; the spec makes individual *states* responsible for deciding what a NUL, form feed, or other control character means in their specific context, starting with the Data state in Module 3. Preprocessing only ever touches CR/LF.
