01 — The Big Analogy

The universal translator with a phrasebook and a numbered code

Imagine an interpreter who can decode a foreign message two ways. If it starts with a recognizable word ("amp", "copy", "hellip"), they flip through a phrasebook looking for the longest word they recognize — not just any match, the longest one, because a short word might accidentally be the start of a longer one. If instead the message starts with a number ("#65" or "#x41"), they skip the phrasebook entirely and just look the number up directly on a giant numbered chart of every symbol that exists — with one quirk: certain specific "damaged" numbers (zero, out-of-range, and a legacy block of typewriter codes) get mapped to a special "best guess" symbol instead of being read literally. And if the message doesn't start with either a recognizable word or a number, the interpreter shrugs and says "that's not a message at all" — leaving every character exactly where it was, untouched.

02 — What Happens, Step by Step

  1. Data state already consumed the & and switched here. Nothing has been emitted yet.
  2. If we're at EOF, or the next character is whitespace, <, or another &: this was never a character reference. Return "no match."
  3. If the next character is #: this is a numeric reference. Consume optional x/X (hex) or default to decimal, consume digits, optionally consume a trailing ; (parse error if absent), then map the resulting number through the four special cases (0, too-large, surrogate, Windows-1252 range) before producing a final character.
  4. If the next character is alphanumeric: this is a named reference. Look ahead, try the longest prefix that matches a known name first, shrinking one character at a time until something matches or nothing does.
  5. On success: emit the decoded character(s) as a token. On failure: emit a literal & token instead — nothing was consumed beyond the original &, so every subsequent character is still there to be tokenized normally.
  6. Either way, switch back to whichever state sent us here (Data or RCDATA).

04 — The Algorithm, Explained (pseudocode)

function CONSUME_CHARACTER_REFERENCE(tokenizer):
    start = tokenizer.pos
    if tokenizer.atEOF(): return NO_MATCH
    c = tokenizer.peek()
    if c in {TAB, LF, FF, SPACE, '<', '&'}: return NO_MATCH

    if c == '#':
        tokenizer.consume()                       // the '#'
        isHex = tryConsume(tokenizer, 'x' or 'X')
        digits = consumeWhile(tokenizer, isHex ? HEX_DIGIT : DIGIT)
        if digits is empty:
            tokenizer.pos = start
            reportParseError("absence-of-digits...")
            return NO_MATCH
        if tokenizer.peek() == ';': tokenizer.consume()
        else: reportParseError("missing-semicolon...")
        n = parseNumber(digits, isHex ? 16 : 10)
        return mapNumericCodePoint(n)              // handles 0 / too-large / surrogate / windows-1252

    if isAlphanumeric(c):
        for len from MAX_NAME_LENGTH down to 1:
            candidate = tokenizer.peekString(len)
            if candidate in NAMED_REFERENCES:
                tokenizer.pos += len
                if not candidate.endsWith(';'): reportParseError("missing-semicolon...")
                return NAMED_REFERENCES[candidate]
        tokenizer.pos = start
        return NO_MATCH

    return NO_MATCH

Getting a blank or broken result?

"my astral emoji test shows length 1, not 2" — you're probably counting with something codepoint-aware (like spreading a JS string into an array, or Java's codePointCount) instead of raw length. .length (JS) / .length() (Java) count UTF-16 code units, which is exactly what this test wants to see as 2 — see the Unicode prerequisite page if this is surprising.
"my named-reference table lookup never matches anything" — double check you're computing LONGEST_NAME_LENGTH from the table's actual keys, not a hardcoded number that's since drifted out of sync after you added an entry.

07 — Brain Exercise

Before reading the answer: &#0; becomes U+FFFD, but a literal NUL byte typed directly into the Data state (Module 3) is emitted as-is. Both are "a NUL, sort of." Why does the spec treat them so differently?

Reveal the answer

Because they come from different real-world failure modes, and the spec is optimizing for what each one most likely means. A literal NUL byte in a document is almost always a genuine encoding/transmission accident — corrupted bytes, a truncated read, a binary file mistakenly served as text — and preserving it as-is keeps the tokenizer's behavior maximally predictable and debuggable for that accident. &#0;, by contrast, can only appear because someone (or some generator) explicitly typed the six characters &#0; — it's not a transmission accident, it's deliberate text that is, in a Unicode-aware document, requesting a character that fundamentally cannot be validly represented (NUL is disallowed as real character data in this context). U+FFFD is the standard "you asked for something that cannot be here" signal across all of Unicode-aware software, not just HTML — using it here keeps this spec consistent with that much broader convention.

08 — There Are No Dumb Questions

Q: Why does matching need to be "longest match wins" instead of just checking the full real spec table for an exact match with a trailing semicolon?
A: Because the spec explicitly supports legacy references with NO trailing semicolon for a specific subset of names — so &amp (no semicolon) must still resolve, and the algorithm can't know in advance whether more characters after it were meant to extend the name or not. Longest-match resolves this deterministically: try the biggest plausible name first, and only fall back to something shorter if the bigger one isn't real.
Q: If my named-reference table only has ~25 entries, doesn't that mean this tokenizer gives wrong answers on most real-world HTML?
A: It gives *incomplete* answers on real-world HTML using entities outside the subset (they'll fall back to literal text, same as any genuinely unrecognized name) — but never *wrong* ones for the entities it does know, and the fallback behavior itself is spec-correct. This is exactly the kind of honestly-scoped gap this course's DECISIONS.md exists to make undeniable rather than something you'd have to discover by accident.
Q: Why does a failed named-reference match have to fully backtrack instead of just consuming what it read and moving on?
A: Because those characters weren't actually part of a reference — they're ordinary text that happens to start with a letter, like the "x" in "&xyz;" is just the literal letter x, not evidence of a reference attempt gone wrong. Backtracking to the start is what lets Data state's normal character-by-character loop pick every one of them up correctly afterward.
Q: This module tests CHARACTER_REFERENCE_IN_RCDATA directly, by force-setting state — isn't that cheating, since RCDATA state itself doesn't exist yet?
A: It's the same technique Module 1 used to test COMMENT_START before Module 13 existed — deliberately testing one seam of the machine in isolation, without needing every upstream state built first. It's not cheating; it's exactly what lets this course verify each state independently instead of only being able to test anything once all 68 states are finished.
