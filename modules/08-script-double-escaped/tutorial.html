01 — The Big Analogy

A password that's case-sensitive exactly once

Every door badge in this whole building system has been case-insensitive so far — "TEXTAREA" and "textarea" open the same door. But this one specific inner door, the one that leads deeper into a comment-within-a- comment, has a badge reader that was installed by a different contractor and never got the memo: it checks your badge letter-for-letter, exact case, no exceptions. Type your badge as "SCRIPT" and this one door simply doesn't recognize it as the word "script" at all — not "access denied," but genuinely "I don't know what you're asking for," and you get redirected back out to the ordinary hallway instead.

02 — What Happens, Step by Step

  1. Module 7 already emitted < and reconsumed a letter here — we're mid-word, building a candidate name one letter at a time, exactly as typed (not lowercased).
  2. Every letter gets appended to the buffer and emitted as a character token immediately — there's no batching or deferring here.
  3. The moment a terminator (whitespace, /, >) arrives, check: does the buffer read exactly "script", case-sensitively?
  4. If yes: enter double-escaped mode — a near-twin of single-escaped mode, with one behavioral difference (< is emitted immediately, not deferred).
  5. Double-escaped mode watches for its own </ to detect the nested script's real close — which flips into a mirror-image state watching for the buffer to spell "script" again, this time to leave double-escaped mode.
  6. From any depth, seeing a real --> always exits all the way back to plain script data in one step — nesting doesn't add extra "levels" you have to unwind one at a time.

03 — A Concrete Map of This Module's State

Three levels, and where "-->'" sends you from each:

SCRIPT_DATA (plain)
<!-- ... SCRIPT_DATA_ESCAPED (single) ...
<script> ... SCRIPT_DATA_DOUBLE_ESCAPED (double) ... </script>
... back in SCRIPT_DATA_ESCAPED ...
--> ALWAYS exits straight back to SCRIPT_DATA, from any of the three levels

04 — The Algorithm, Explained (pseudocode)

function SCRIPT_DATA_DOUBLE_ESCAPE_START_STATE(tokenizer):
    c = tokenizer.consume()
    if c in {TAB, LF, FF, SPACE, '/', '>'}:
        if tokenizer.tempBuffer == "script":       // exact, case-sensitive
            tokenizer.state = SCRIPT_DATA_DOUBLE_ESCAPED
        else:
            tokenizer.state = SCRIPT_DATA_ESCAPED
        emit CharacterToken(c)                     // always emitted, either way
        return
    if c is an ASCII letter:
        tokenizer.tempBuffer += c                  // exact case, NOT lowercased
        emit CharacterToken(c)
        return                                      // stay, keep building
    tokenizer.state = SCRIPT_DATA_ESCAPED
    reconsume c there                                // (no-op if EOF)

05 — Limits / What You Cannot Do Yet

Can't do yet

  • Enter any of this from real markup — needs Module 9's <script> opening tag
  • Handle a THIRD level of nesting (the spec doesn't define one — this is the deepest the mechanism goes)

Can do

  • Correctly tokenize a real, fully nested hidden-comment script body end to end
  • Correctly apply the case-sensitive "script" check in both directions
  • Correctly exit from any nesting depth straight back to plain script data

Getting a blank or broken result?

"my uppercase test doesn't behave differently from lowercase" — you're almost certainly lowercasing (or uppercasing) the buffer somewhere before comparing. Search for any .toLowerCase() / Character.toLowerCase() call near the temp-buffer append — there shouldn't be one in these two states.
"nested script never exits back to plain SCRIPT_DATA" — check the dash-dash state's '>' branch targets SCRIPT_DATA directly, not SCRIPT_DATA_ESCAPED.

07 — Brain Exercise

Before reading the answer: this course caught the case-sensitivity quirk by writing a test that deliberately used uppercase input and checking the resulting state. If this course's test suite had only ever used lowercase "script" in every test (a very natural thing to do by accident, since almost everyone writes lowercase HTML), would any test have failed to catch a bug that accidentally made the comparison case-insensitive?

Reveal the answer

No — and that's exactly the point. A case-insensitive comparison and a case-sensitive one produce identical results for every all- lowercase input; there is no lowercase-only test that could ever distinguish them. This is precisely why this module deliberately verified the bug live (see DECISIONS.md and both CODE_WALKTHROUGH.md files): a test suite can only prove what it actually exercises, and a quirk this specific requires a test specifically shaped to expose it, not just "more" tests in general. It's the same lesson Module 7 landed on from the opposite direction (a real bug that slipped past a full suite) — here, the lesson is what it actually takes to catch one like it on purpose.

08 — There Are No Dumb Questions

Q: Why would this case-sensitivity quirk exist at all — was it intentional?
A: Most likely a consequence of how this exact mechanism was reverse-engineered from real early-2000s browser behavior rather than designed from scratch — HTML5's tokenization spec was written to formally describe what shipping browsers already did (for compatibility), including their accidental quirks, not to design an idealized new grammar. This is one of several places in this course's spec source where "why is it like this" has a historical rather than a logical answer.
Q: In practice, does anyone actually write <SCRIPT> in uppercase inside a hidden comment?
A: Essentially never on purpose today — but the spec still has to define correct, deterministic behavior for it, because "never happens on purpose" isn't the same guarantee as "never happens," and a tokenizer with undefined behavior for unusual-but-possible input is a security liability, not just a correctness one (Track 2's Module A3 covers this class of concern directly).
Q: Now that Modules 6, 7, and 8 are all built, is the entire <script> tokenizing story finished?
A: The content-handling states are complete — but the opening <script> tag itself (and every other tag in this course, generically) still needs Module 9 before any of this machinery can be reached from real markup. Everything from Module 6 onward has been tested by force-setting a starting state precisely because that producer doesn't exist yet.
