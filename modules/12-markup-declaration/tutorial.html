01 — The Big Analogy

A bouncer checking three specific badges, then a lost-and-found bin for everything else

Right after the door marked <!, a bouncer checks exactly three things, in order, without ever guessing: "does this start with two dashes? Does it spell DOCTYPE, in any mix of capitals? Does it spell [CDATA[ exactly?" Match one, and you're waved through to that specific room. Match none, and — rather than turning you away — the bouncer shrugs and drops you in a lost-and-found bin (a "bogus comment"): everything about you gets written down as-is, right up until someone closes the bin's lid with a >. Nothing is ever rejected outright; unrecognized input always ends up somewhere real.

02 — What Happens, Step by Step

  1. Module 9's <! handoff arrives here with nothing yet consumed past the !.
  2. Check, without consuming: do the next two characters spell --? If so, consume them, start a real comment token, and head into Module 13.
  3. Otherwise check: do the next seven characters spell DOCTYPE, in any mix of upper/lowercase? If so, consume them and head into Module 14.
  4. Otherwise check: do the next seven characters spell [CDATA[, exact case? If so, consume them and head into Module 15.
  5. None of the three matched: report a parse error, start a comment token, and fall into Bogus Comment — consuming nothing extra, so whatever didn't match is still sitting there, about to become the comment's first characters.
  6. Bogus Comment just accumulates characters into that comment's data until > (or EOF) ends it — no further structure, no further checks.

04 — The Algorithm, Explained (pseudocode)

function MARKUP_DECLARATION_OPEN_STATE(tokenizer):
    if tokenizer.matchLiteral("--"):
        consume 2 characters
        tokenizer.currentToken = new CommentToken()
        tokenizer.state = COMMENT_START
        return
    if tokenizer.matchCaseInsensitive("DOCTYPE"):
        consume 7 characters
        tokenizer.state = DOCTYPE
        return
    if tokenizer.matchLiteral("[CDATA["):
        consume 7 characters
        tokenizer.state = CDATA_SECTION
        return
    reportParseError("incorrectly-opened-comment")
    tokenizer.currentToken = new CommentToken()
    tokenizer.state = BOGUS_COMMENT   // nothing consumed -- reconsume implicit

Getting a blank or broken result?

"my <?xml?> test expects the wrong comment data" — this bit us during this module's own construction: the leading ? IS part of the bogus comment's data (Module 9 reconsumes it, doesn't discard it). If your expected value is missing the leading ?, that's the bug — see DECISIONS.md's "What We Proved" for exactly how this was caught.
"DOCTYPE matches only in one case" — check you're using a genuinely case-insensitive comparison (lowercase both sides before comparing), not a literal string match.

07 — Brain Exercise

Before reading the answer: this module's own test suite caught a real error in the assumption carried over from Module 9 (that the ? gets discarded, when it's actually reconsumed). Module 9 was built and fully tested, with all its tests passing, several modules before this mistake was caught. How could a wrong assumption survive an entire module's worth of passing tests undetected?

Reveal the answer

Because Module 9's own tests never needed to know or check what the reconsumed character eventually becomes — they only needed to confirm that <? correctly switches to BOGUS_COMMENT and reports a parse error, both of which were true regardless of whether the ? was reconsumed or discarded (since BOGUS_COMMENT wasn't built yet, either choice produced the identical observable result at the time: a NotImplementedError pointing at Module 12). The detail only became observable once Module 12 actually built the state that consumes that reconsumed character. This is a real, general lesson: a seam can be correctly wired and fully tested while still hiding an untested assumption about what happens once the room behind it is finally built — which is exactly why this course insists on tracing full round trips, not just isolated seams, as each new module comes online.

08 — There Are No Dumb Questions

Q: Why does <?xml version="1.0"?> (a real, valid XML processing instruction) get turned into an HTML comment instead of being recognized properly?
A: Because HTML's tokenizer isn't an XML tokenizer, and processing instructions were never part of HTML's own grammar — a "?" right after "<" was never valid HTML tag syntax to begin with. The spec's answer to "what should happen with syntax that was never valid" is consistently "don't reject it outright, fold it into the nearest sensible bucket" — here, that bucket is a comment, since a comment's job (hold arbitrary text, don't parse it as markup) is the closest fit.
Q: Why is "--" case-sensitive when "DOCTYPE" isn't?
A: Dashes have no case to be insensitive about — "case-insensitive" only has meaning for letters. The real distinction isn't "some declarations get special leniency and others don't"; it's that DOCTYPE, as a keyword written by human authors for decades before HTML5 formalized its rules, needed to tolerate whatever capitalization convention any given era or author preferred, while "--" as a two-character comment-opening punctuation mark never had multiple "spellings" to begin with.
Q: Does a bogus comment ever get treated differently from a "real" comment once tokenizing is done?
A: Not by the tokenizer — both are indistinguishable `CommentToken`s in the output stream by the time this module is done with them. Any distinction between "this was a well-formed HTML comment" and "this was salvaged from malformed input" exists only in the tokenizer's parse-error log, not in the token itself.
