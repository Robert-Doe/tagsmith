01 — The Big Analogy

A "read literally, don't translate" stamp on a passage

Imagine a translator working through a document who occasionally hits a passage stamped "QUOTE VERBATIM — DO NOT INTERPRET." While inside that stamped section, they copy every character exactly as written, symbol for symbol, no matter how foreign-looking or markup-like it appears — until they spot the specific closing mark that ends the stamp's effect. One lone character that merely resembles the closing mark doesn't end anything; only the complete, exact three-character sequence does.

02 — What Happens, Step by Step

  1. Module 12 already consumed [CDATA[. Everything from here is literal content until proven otherwise.
  2. At every position, check: do the next three characters spell ]]> exactly? If so, consume all three and return to Data state — the section is over.
  3. If not, consume and emit just the current character as an ordinary CharacterToken, then check again at the new position.
  4. NUL is a parse error but still emitted literally, and EOF is a parse error too, but still emits everything collected plus a final EOF token — both handled exactly like Data state.

04 — The Algorithm, Explained (pseudocode)

function CDATA_SECTION_STATE(tokenizer):
    if tokenizer.matchLiteral("]]>"):
        consume 3 characters
        tokenizer.state = DATA
        return
    if tokenizer.atEOF():
        reportParseError("eof-in-cdata")
        emit EOFToken
        halt
        return
    c = tokenizer.consume()
    if c is NUL: reportParseError("unexpected-null-character")  // still emitted
    emit CharacterToken(c)

07 — Brain Exercise

Before reading the answer: this module's own walkthrough found that weakening the close-check from three characters to two didn't break a single existing test — every test's ]] happened to be followed by a real > anyway. It took a specifically constructed input, ]]x]]>rest, to expose the bug. What made that specific input the right one to reach for, instead of just trying random strings?

Reveal the answer

Because exposing this exact bug requires an input where the WEAKENED check matches (two brackets present) at a position where the FULL, correct check would NOT match (the third character isn't really >) — that's the precise condition under which the buggy code's blind third consume() swallows the wrong character. ]]x]]>rest was built by construction, not by guessing: two brackets, then a character that definitely isn't >, then a real close later so the section still eventually ends normally. This is a general debugging skill this course has now demonstrated several times (Modules 7, 8, 12, 13, and 14 each did some version of it): when you suspect a check is too loose, don't just retest existing cases — construct the minimal input that makes the loose version and the strict version disagree, on purpose.

08 — There Are No Dumb Questions

Q: The tutorial keeps saying "foreign content" for CDATA — what does that actually mean?
A: It refers to SVG and MathML content embedded inside an HTML document — two other markup languages that DO use CDATA sections in their native form, unlike ordinary HTML. A real browser only treats <![CDATA[ this way when the tokenizer is currently inside one of those embedded regions; outside of them, real browsers treat it as a bogus comment instead (Module 12's fallback). This course's tokenizer takes the CDATA path unconditionally, because knowing "am I inside SVG/MathML right now" is tree-construction context this course's Track 1 doesn't track — documented explicitly in Module 12's DECISIONS.md as the same kind of limitation Module 9 first identified for RCDATA switching.
Q: Is CDATA content able to contain character references, like attribute values or Data state can?
A: No — CDATA is specifically "read literally, don't interpret anything," which is the whole reason it exists as a distinct mechanism. If `&` appeared inside a real CDATA section, it would come through as four literal characters (`&`, `a`, `m`, `p`) plus a semicolon, never decoded to `&`.
