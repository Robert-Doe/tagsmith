01 — The Big Analogy

The airport customs officer

Picture a customs officer standing at one checkpoint, watching a line of travelers pass through one at a time. For almost every traveler, the officer just waves them straight through into the country — that's a plain character becoming a `CharacterToken`. But two specific travelers get special treatment: anyone carrying a package marked "&" gets redirected to a separate inspection room (the character-reference room), and anyone carrying a package marked "<" gets redirected to a different inspection room (the tag room). The officer doesn't inspect the package themselves — that's not their job. They just point, say "go there," and immediately turn to face the next traveler in line.

02 — What Happens, Step by Step

  1. Is there a next character at all? If not, emit an EOF token and stop — unchanged from Module 1.
  2. Consume the next character.
  3. Is it &? Switch to the character-reference-in-data state. Emit nothing. Stop processing this character — the next step() call picks up in the new state.
  4. Is it <? Switch to the tag-open state. Same as above: emit nothing, hand off entirely.
  5. Is it NUL (U+0000)? Record a parse error, but still emit it as a CharacterToken — tokenizing does not stop for a parse error.
  6. Anything else: emit it as a CharacterToken, verbatim.

04 — The Algorithm, Explained (pseudocode)

function DATA_STATE(tokenizer):
    if tokenizer.atEOF():
        emit EOFToken
        tokenizer.halted = true
        return

    c = tokenizer.consume()

    if c == '&':
        tokenizer.state = CHARACTER_REFERENCE_IN_DATA
        return                      // emits nothing

    if c == '<':
        tokenizer.state = TAG_OPEN
        return                      // emits nothing

    if c == NUL:
        reportParseError("unexpected-null-character")
        emit CharacterToken(c)      // still emitted, per THIS spec snapshot
        return

    emit CharacterToken(c)          // the common case

07 — Brain Exercise

Before reading the answer: Module 1 threw a NotImplementedError naming Module 4 directly from inside dataState() when it saw &. Module 3 no longer does that — it just switches state and returns, letting the generic fallback in step() throw instead. Both approaches produce the exact same observable error. So why does the change matter?

Reveal the answer

Because Module 1's version was a lie that happened to look correct: it hardcoded knowledge of what error message a & "should" produce, rather than actually implementing the spec's real behavior (switch state) and letting the truth fall out naturally. The tell is what happens when Module 4 actually gets built: with Module 1's approach, you'd have to remember to go delete that hardcoded throw. With Module 3's approach, Module 4 just needs to add a real handler for CHARACTER_REFERENCE_IN_DATA to the dispatch table, and the generic fallback simply stops firing for that state — zero code in dataState() needs to change ever again. That's the difference between code that looks right today and code that's *structured* to become more right tomorrow without rework.

08 — There Are No Dumb Questions

Q: Why does emitting a literal NUL character token matter — how often does real HTML actually contain a NUL byte?
A: Rarely by accident, but not never — and it's a classic security-relevant edge case: NUL-byte injection has historically been used to try to confuse parsers or filters that treat NUL as a string terminator (common in C-derived string handling) differently than a spec-compliant tokenizer does. Getting this exact, spec-mandated behavior right is directly relevant to Track 2's security modules later in this course.
Q: Since '&' and '<' don't emit anything, how does a real page's text ever actually get split into the right CharacterTokens around a tag?
A: The split happens implicitly, for free, as a side effect of state switching — every character consumed *before* the '<' already got its own CharacterToken emitted in previous loop iterations; the '<' just marks the boundary where Data state stops being in charge. Nothing needs to "look back" or buffer text waiting to see if a tag is coming.
Q: Is "parse error" the same thing as "this is invalid HTML, reject it"?
A: No — this is one of the most-misunderstood parts of the HTML5 parsing model for newcomers. A parse error is a signal ("something unusual happened here"), not a stop condition. HTML tokenizers and parsers are specifically designed to always produce *some* well-defined output for *any* input, valid or not — that's precisely why browsers can render malformed HTML instead of showing a blank error page.
Q: You mentioned the modern spec replaces NUL with U+FFFD instead of emitting it literally — which one should I actually cite in my comprehensive exam?
A: Know both, and know which document you're citing. This course intentionally implements the exact W3C Last Call snapshot linked in ROADMAP.md, because that's the artifact you're building against — but a defense committee could reasonably ask about the current WHATWG Living Standard's behavior too, since that's what real shipping browsers implement today. Being able to name the difference and explain why specs evolved (implementer/security feedback after the fact) is stronger than only knowing one version by rote.

09 — What's Next

Module 4 finally builds a real handler for CHARACTER_REFERENCE_IN_DATA — the "inspection room" this module has been correctly routing travelers to, but leaving empty. It implements the spec's general "consume a character reference" algorithm: named references like &amp;, decimal references like &#38;, and hex references like &#x26;, all decoding to the same character.
