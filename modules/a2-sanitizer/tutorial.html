This module is Module A1's tree builder put to work: removing dangerous elements and attributes from a real, parsed structure instead of pattern-matching raw text.

01 — The Big Analogy

The metal detector vs. the airport X-ray

A metal detector (the regex-based sanitizer) reacts to a signal shape: it beeps at anything with the right metallic profile, wherever it appears on your body. It has no idea whether that shape is a belt buckle in your bag's decorative pattern or a real weapon in your pocket — it just pattern-matches. An X-ray scanner (this module's real sanitizer) instead builds an actual picture of what's inside the bag — what's really a solid object, where its boundaries really are — before deciding what's dangerous. This module's whole lesson is that "does this text merely look like a script tag" and "is this actually a script element, structurally" are different questions, and only one of them is safe to base a security decision on.

02 — What Happens, Step by Step

  1. Parse the input HTML with the real tokenizer and Module A1's tree builder — never touch the raw source text again after this step.
  2. Walk the resulting tree. For every element, check its tag name against a small "dropped elements" list (starting with script); if it matches, the entire element — tags and all its content — is discarded, not kept as unwrapped text.
  3. For every element that survives, check each of its already-parsed attributes: drop any whose name starts with on (event handlers), and drop href/src specifically when their value starts with javascript:.
  4. Serialize whatever tree survives back into an HTML string, re-escaping & and < in text content so the output is safe to embed again.

03 — A Concrete Map of This Module's State

The exact divergence this module measured, both real, both run:

RCDATA case

04 — The Algorithm, Explained (pseudocode)

function SANITIZE(html):
    tree = TREE_BUILDER(html).run()          // Module A1's real tokenizer-driven parse
    return SERIALIZE( SANITIZE_NODE(tree.children) )

function SANITIZE_NODE(node):
    if node is ElementNode:
        if node.tagName in DROPPED_ELEMENTS:
            return null                       // whole subtree gone, not unwrapped
        clean = ElementNode(node.tagName, FILTER_ATTRIBUTES(node.attributes))
        for child in node.children:
            cleanChild = SANITIZE_NODE(child)
            if cleanChild != null:
                clean.children.append(cleanChild)
        return clean
    if node is TextNode or CommentNode:
        return copy of node                   // passed through unchanged

function FILTER_ATTRIBUTES(attributes):
    return [a for a in attributes if not DANGEROUS(a)]

function DANGEROUS(attr):
    if attr.name starts with "on": return true
    if attr.name in {"href","src"} and attr.value starts with "javascript:":
        return true
    return false

function SERIALIZE(node):
    if node is TextNode: return ESCAPE(node.data)     // re-escape & and < !

05 — Limits / What You Cannot Do Yet

Can't do yet

  • A production-grade allowlist — this module's dangerous-element/attribute lists are small and illustrative (see DECISIONS.md), not a complete real-world policy (no style, no iframe, no data: URLs, no foreign content)
  • Handle CSS- or SVG-context injection — those are different attack surfaces this module doesn't touch
  • Mutation XSS, where a sanitizer's own safe-looking output becomes unsafe after a browser re-parses and "fixes up" malformed structure — that's Module A3

Can do

  • Remove real <script> elements completely, with zero content leakage, verified by direct string checks
  • Strip dangerous attributes while preserving every safe attribute on the same element
  • Prove — not just claim — the exact regex-vs-tokenizer divergence ROADMAP.md predicted for this module, in both languages independently

Getting a blank or broken result?

"my sanitized output still contains 'alert'" — check that DROPPED_ELEMENTS actually contains the lowercase tag name your input uses; tag names are lowercased by the tokenizer itself (Module 9), but a typo in this module's own set literal won't be caught by that.
"my serialized output looks like double-escaped HTML" — make sure escapeText/escapeAttrValue are only called once, at serialization time, on already-decoded values — calling them earlier (e.g. inside sanitizeNode) and then again in serializeNode would escape twice.

07 — Brain Exercise

Before reading the answer: the naive regex sanitizer's bug in this module is a false positive — it deletes real page content, but no actual attack survives it either (both approaches agree in every case where a real `<script>` element is truly present). Given that, is the naive regex sanitizer still meaningfully "unsafe" to ship, or is this module's finding really just a correctness/availability bug rather than a security one?

Reveal the answer

It's genuinely both, and the security framing matters even though this specific verified case is a false positive. A sanitizer whose matching logic doesn't track the tokenizer's real modes has no principled reason to only fail in the "safe" direction — the same root cause (pattern-matching text instead of tracking RCDATA/RAWTEXT/script-data boundaries) is exactly the category of bug that, with a differently constructed input, produces the opposite, dangerous kind of failure: a real `<script>` that the regex fails to recognize as one (a false negative) because it's positioned somewhere the regex's assumptions don't hold — inside a RAWTEXT element with an unusual nesting, or split across what looks like two tags to a regex but is one tag to a real tokenizer. This module chose to build and verify the false-positive case because it's clean and easy to confirm unambiguously; the underlying defect is the same one a false-negative would come from.

08 — There Are No Dumb Questions

Q: Why does this module's real bug-hunting story (documented in Module A1's DECISIONS.md) matter for a sanitizer specifically, more than for, say, a syntax highlighter?
A: Because a sanitizer's entire job is drawing a correctness boundary a security decision depends on. A syntax highlighter that mishandles a mismatched end tag inside RCDATA produces an ugly but harmless rendering glitch. This module's sanitizer making the identical mistake would mean either legitimate content gets destroyed (this module's verified case) or, in a differently shaped input, a dangerous element could be misclassified as safe. The same underlying tokenizer correctness matters everywhere, but the stakes of getting it wrong are not the same in every application built on top of it.
Q: Couldn't you just improve the regex instead of building a whole tokenizer-based sanitizer?
A: You could patch this exact case, and the next one, and the one after that — real-world regex-based sanitizers have a long, documented history of doing exactly this, one CVE at a time. The structural problem doesn't go away: a regex has no notion of "which mode is the tokenizer in right now," so it's always one clever input away from being wrong again. A real tokenizer tracks that mode as a first-class fact, which is why this module's sanitizer doesn't need a special case for the `<title><script>` scenario at all — RCDATA-awareness is just Module 5's tokenizer doing what it already does.
Q: Is dropping a `<script>` element's content, rather than keeping it as unwrapped text, always the right choice?
A: Not universally — it's a deliberate, conservative policy choice for this module (see DECISIONS.md), not a fact forced by the tokenizer. `<script>alert(1)</script>` unwrapped to bare text `alert(1)` would still be inert as plain page text. But a general sanitizer can't assume that's true for every disallowed element in every context (some elements' content is meaningful even after their tags are stripped, depending on where the sanitized output ends up), so removing the whole subtree is the safer default this module chose.
