PrerequisiteCode Points vs. UTF-16 Code Units

The Big Analogy

A person's real identity is their full legal name — that's who they are, one single fact. But when you write that name on a postcard, sometimes it fits on one card, and sometimes the name is so long you need two postcards taped together, in order, to write the whole thing. Anyone reading just the second postcard alone would see a meaningless fragment — not a name, just half of one.

A Unicode code point is the "real identity" — a single number that names one character, like U+0041 for the letter A, or U+1F600 for 😀. A UTF-16 code unit is a postcard: a 16-bit chunk. Most code points (everything in the "Basic Multilingual Plane," which covers virtually all of English, Latin-script European languages, and the ASCII characters the tokenizer cares about most) fit on exactly one postcard. But code points above U+FFFF — most emoji, many rare CJK characters, some mathematical symbols — need two code units, called a surrogate pair, taped together in a specific order.

Why this is a prerequisite, not trivia

Both JavaScript strings and Java String/char are UTF-16 code-unit sequences, not code-point sequences. That means:

  • JavaScript's str[i], str.charAt(i), and Java's str.charAt(i) all give you one code unit — which might be half of a real character, if that character happens to be a surrogate pair.
  • str.length (JS) and str.length() (Java) count code units, not "characters" in the everyday sense.
Where this could bite you in this course

Every state machine transition in the spec is phrased in terms of "the current input character" as a code point. For tag names, attribute names, and the ASCII punctuation the tokenizer branches on (<, &, >, quotes, -, !), this distinction never matters — they're all single-code-unit ASCII. It starts to matter once character data (text content, attribute values) can contain arbitrary user text, like an emoji typed into a <textarea>. This course's Module 1 Character token intentionally models one character as one code unit, which is a known, documented simplification — not an oversight — until it's revisited.

Concrete example

// JS
"A".length        // 1  — one code unit, one code point, no surprise
"😀".length        // 2  — one code point, but TWO code units (surrogate pair)

// Java
"A".length()       // 1
"😀".length()       // 2

How this connects

This matters wherever the spec talks about consuming "the next input character" — see Input Streams & Iterators. It's also the reason Java's Module 1 CharacterToken stores a char (one UTF-16 code unit) rather than a full code point — a convention documented in that module's DECISIONS.md.
