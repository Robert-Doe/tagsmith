The Big Analogy

Picture a board game with 68 numbered rooms. You are a single token standing in exactly one room at a time — never two, never none. Each room has a little rulebook taped to the door: "if you draw a card that says X, walk to room 12. If it says Y, walk to room 40. Otherwise, stay here and do nothing." That's it. That's the entire game. You never need to remember which rooms you visited before — the rulebook for the room you're standing in right now is the only thing that decides your next move.

That board game is a finite state machine (FSM), and it is exactly the model the HTML5 tokenizer is built on. The spec says so explicitly: "the tokenization stage... consists of ... a state machine."

The four ingredients

  • States — the rooms. The tokenizer has 68 of them (Data, Tag open, Comment end dash, DOCTYPE, ...). Each has a name straight out of the spec's section headings.
  • The current state — which room you're standing in right now. Just one variable, holding just one value, at any moment.
  • Input — the card you draw each turn. For the tokenizer, that's the next character from the HTML text.
  • Transitions — the rulebook. Given the current state and the input character, exactly one thing happens next: maybe you move to a new state, maybe you stay, and maybe something gets produced (a token) along the way.

Why "finite" and why it matters here

"Finite" just means the room count is fixed and known in advance — 68, not "as many as needed." That's a big deal for an implementer: it means you can draw the entire map before writing a single line of real logic. Module 1 of this course does exactly that — it builds all 68 rooms as empty, correctly-labeled placeholders before a single one of them does real work.

The one rule that makes this tractable

The next state depends only on the current state and the current input character — never on anything that happened three moves ago. This is what lets the spec describe 68 rooms independently, each in its own short section, instead of one giant tangled paragraph of "it depends."

Pseudocode shape

state = START_STATE
while not done:
    input = next_input_symbol()
    (state, output) = transition(state, input)
    if output: produce(output)

Every single one of the 68 sections in the spec is really just describing one branch of that transition() function. Nothing more exotic is happening under the hood.
